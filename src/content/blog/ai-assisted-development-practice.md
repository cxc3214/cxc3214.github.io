让 AI 修改博客时，“页面能打开”很容易成为过早的结束条件。导航可能指向旧网址，文章可能没有进入构建，修订日期可能不正确。本站的验收方法是把任务写成具体可观察的行为，再选择能证明这些行为的检查。

## 先把任务从形容词改成行为

“更专业”“更完整”无法直接测试。以文章页为例，可以把要求写成：读者点击目录后能到达对应段落；每篇文章显示作者和日期；旧 URL 仍可打开；手机上横向滚动代码块时，整张页面不会跟着变宽。

给 AI 的上下文也应包括限制。本站应用下载字段在 `src/config/apps.json`，它们不是博客改版时可以随意改写的装饰文字。发布商账号、文件哈希、APK 路径这些值应该由已有来源决定，不能由模型猜测。

一个可复用的任务说明可以写成：

```text
目标：为现有文章增加自动目录。
输入：PostLayout.astro 和 Markdown 渲染器返回的 headings。
行为：只列二级标题；链接准确；窄屏可读。
边界：保持文章 URL、正文、下载配置不变。
验收：构建成功；每个目录 href 都能匹配正文 ID；浏览器点击有效。
```

这个说明刻意小于“改好整个博客”，因为目录和文章内容是不同的责任。把紧密耦合的修改放在一起，把可独立验证的目标拆开，比并行生成大量文件更容易发现遗漏。

## 源码测试能防什么，不能防什么

本站原有的测试会检查关键页面是否存在、AdSense ID 是否一致、APK URL 是否版本化、包名和 SHA-256 字段是否符合格式。这类测试适合防止误删字段和拼写错误。

但正则匹配到一个组件名，不能证明浏览器真的渲染了它。文章包含多个标题也不代表论证成立。对于“低价值内容”，测试最多证明页面有正文和元信息，不能自动判断原创性，更不能模拟 Google 的审核。

因此，不应该为了让测试变绿，把内容写成刚好满足测试字符串的样子。测试要跟着用户行为走，而不是让文章跟着测试的实现细节走。

## 构建产物是第二层证据

```sh
npm test
npm run build
npm run preview -- --host 127.0.0.1
```

构建后直接检查 HTML，能发现内容集合、路由生成和元数据拼接的问题。例如目录里出现 `#下载前先看版本`，产物里必须存在同名 ID；canonical 必须指向该文章而不是首页；引用的图片必须进入公开目录。

这里适合自动化，因为要求是离散而明确的：“目标存在”或“不存在”。相比之下，文章是不是过于重复、例子是否讲清楚、提醒是否喧宾夺主，需要阅读实际内容。

## 浏览器检查要包含一次失败路径

只点首页主按钮，通常只能证明最顺的路径。本站文章含代码块和表格，至少要在窄屏看一次；应用下载页则应确认版本说明与按钮对应，并查看隐私入口是否可达。

失败路径不一定意味着破坏性测试。输入一个不存在的文章地址，确认有可理解的 404；用键盘聚焦目录链接，确认看得见焦点；刷新深层路径，确认没有只在客户端导航时才能打开。这些只读操作就能暴露许多发布问题。

还要避免一个常见报告错误：代理在自己的浏览器标签看到了结果，并不代表用户当前窗口也看到了。本文站点的协作过程就需要区分“页面已生成”“页面已打开”“页面已交付给用户”。截图证明的是截图时刻的页面，不能替代当前窗口状态。

## 发布后的检查不能省略

本地预览通过后，仍应对照部署提交和公开域名。网络缓存、构建分支和上传路径都可能让线上结果不同。最终报告应该说清楚哪一层通过了，不能把“准备好发布”写成“已上线”。

| 证据 | 可以支持的结论 | 不能替代的检查 |
| --- | --- | --- |
| 源码测试通过 | 已编码的约束未被破坏 | 页面可用性、文章质量 |
| 构建成功 | 静态产物生成成功 | 公网部署是否更新 |
| 浏览器点击成功 | 当前页面上的该路径可用 | 所有路径、所有设备 |
| 生产页面核对 | 当前发布内容可以访问 | 平台未来审核结果 |

## 我的取舍：把复核时间留给不确定的地方

不是每个文字修改都值得新写一套测试。修正一个错别字，检查差异即可；改文章路由，就值得运行全站内部链接检查。AI 生成代码越快，越应该把时间留给可能影响读者的地方。
