imspring.cn 同时承载文章、项目说明和 Android 应用下载。把所有内容堆在首页，很容易变成一张入口清单：访问者知道我做了哪些东西，却不知道哪篇内容能解决他的问题。本文记录本次怎样重新分配页面职责，以及为什么保留一些看起来“不够自动化”的做法。

## 首页先回答读者能得到什么

改版前的首页首屏以应用下载为中心，文章位于下方，而且按首次发布时间排序。一篇实质修订的技术笔记，可能始终排在较早发布的介绍文章后面。这个顺序对“寻找最新可用信息”的读者不友好。

现在首页提供一个具体的阅读起点，再按三个主题组织文章：网站构建与发布、开发与交付、数据与产品设计。应用入口仍然保留，但功能细节交给专门页面。这样首页承担的是选择任务，而不是把所有内容重复一遍。

这项调整不依赖访问量预测。更直接的验收方法是请读者完成三件事：找到网站发布的检查步骤，找到 APK 校验说明，找到作者的纠错入口。如果只能找到“欢迎来到我的网站”，信息架构还没有起作用。

## 一种内容只保留一个主要地址

本站把长文放在 `/blog/`，项目介绍放在 `/projects/`，应用功能、版本和隐私放在 `/apps/`。它们可以互相链接，但不应该复制同一段长正文。

| 页面 | 主要回答 | 不适合塞进来的内容 |
| --- | --- | --- |
| 首页 | 这里有什么、从哪里开始 | 全部安装步骤和完整文章 |
| 文章 | 一个问题怎样分析与验证 | 没有解释的外链合集 |
| 项目页 | 入口、用途、限制与相关阅读 | 对每个版本重复维护下载值 |
| 应用页 | 功能、兼容性、文件与隐私 | 泛泛的个人介绍 |
| 关于与联系 | 谁维护、怎样写、怎样纠错 | 不必要的个人隐私 |

例如 APK 校验的通用方法放在[这篇笔记](/blog/android-apk-download-verification/)，下载页则显示当前目录的文件信息。读者可以沿链接了解方法，维护者也不必在每个介绍页同步一整篇教程。

## Markdown 元数据不只是给搜索引擎看的

一篇文章至少需要标题、摘要、首次发布时间、主题和适用范围。本站还区分“仓库实践”“排查记录”“技术指南”“设计笔记”，让读者在看到代码前知道它代表哪一种证据。

```yaml
date: 2026-06-14
updated: 2026-09-19
topic: web
kind: 仓库实践
scope: 基于本站配置；不同项目需要核对自己的构建环境。
```

`date` 不因为修改了几句话就重置。`updated` 用于实质修订，在文章顶部可见，并参与归档排序。这样既不伪装成一篇新文章，也不会把旧配置包装成永久有效的结论。

如果只是构思某个功能，应归为设计笔记，示例数据明确标注。读者有权知道“这段方案解释得通”和“这段方案已经上线验证”之间的差别。

## 为什么先用静态页面

本站目前不需要注册账号、评论数据库或登录后内容。文章通过 Astro 在构建时生成 HTML，适合这个维护规模。内容保存在仓库中，修改前后可比较，静态产物也便于迁移。

代价是每次修改都需要重新构建和发布。对于需要分钟级更新的数据，应该在独立服务里解决，而不是让博客承担所有状态管理。本站因此把主站文章与独立工具站分开：主站解释方法，子站提供对应服务，各自说明隐私和使用边界。

## 如何判断一次修订完成

我把修订拆成内容、链接和显示三层。内容层看是否补充了具体问题和证据，链接层看旧地址和目录是否仍能到达，显示层看窄屏是否能读代码和表格。这些都比单纯增加一段字更可检查。

文章的目录直接来自 Markdown 渲染结果，相关阅读从同主题文章优先选择。它们不要求读者安装插件或启用复杂的客户端应用，禁用 JavaScript 后仍能阅读正文和跟随链接。

这次修订仍有边界：页面结构变好不代表内容一定被搜索引擎收录，也不代表 AdSense 必然通过。网站最终应当依靠持续的项目记录与纠错积累，而不是把一次改版当作终点。
