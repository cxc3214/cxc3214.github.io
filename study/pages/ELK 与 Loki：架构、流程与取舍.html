一条日志的两种命运

ELK 把日志里的每个词都编进索引，查什么都快，但贵；Loki 只给日志贴几个标签，正文压缩扔进对象存储，便宜，但查询要靠扫描。下面用动画走一遍两套系统的结构、写入流程和查询流程，最后对比取舍。

2026-10-06T09:12:03Z ERROR api-gateway user=8812 upstream timeout after 3000ms
ELK解析成字段，拆成词，全部进倒排索引
Loki贴上 {app, level} 标签，正文压缩成 chunk

核心差异：索引什么

  
两套系统几乎所有的优缺点，都源于这一个设计选择。看看同一行日志进去后分别变成了什么。

  

    
2026-10-06T09:12:03Z ERROR api-gateway user=8812 upstream timeout after 3000ms

    
  

  

    

      

        
ELK：每个词都建倒排索引

        
Logstash 先解析出字段，Elasticsearch 再对文本分词，每个词都记下出现在哪些文档里。

        

        
查 “timeout” 时：直接在词表里找到 timeout，拿到文档 ID 列表，毫秒级命中，与数据总量关系不大。

      

      

        
Loki：只索引标签

        
索引里只有少量低基数的标签，指向存放日志的 chunk，正文一个词都不索引。

        

          app="api-gateway"
          level="error"
          → chunk 07a3
        

        

          
09:12:03Z ERROR api-gateway user=8812 upstream timeout after 3000ms

          正文原样追加进 chunk，再整体压缩写入对象存储
        

        
查 “timeout” 时：先用标签找到相关 chunk，下载、解压，再逐行匹配。标签圈得越小越快，时间范围越大越慢。

逐项对比

  
着色的格子表示这一项上更有优势的一方。

  

    

      
维度ELKLoki

      
        
索引对象所有字段与全文，倒排索引只索引标签，正文压缩存放

        
存储介质本地 SSD 为主，冷数据可用可搜索快照放到对象存储对象存储为主（S3、GCS、MinIO）

        
存储与资源成本高：索引膨胀、副本翻倍、需要大内存（JVM 堆加文件缓存）低：压缩率高，对象存储便宜

        
写入开销重：分词、建索引、段合并都耗 CPU 和 IO轻：追加加压缩

        
全文与任意字段查询快，任意词在大数据量下也是秒级以内先按标签缩小范围再扫描，范围大或标签不准时慢

        
聚合分析强：任意字段 terms、直方图、地理、ES|QL、机器学习异常检测中：LogQL 指标查询（rate、count_over_time、sum by 标签），对高基数字段聚合吃力

        
高基数字段天然支持，user_id、trace_id 都能直接搜不能做标签，否则流数量爆炸；只能在查询时解析过滤

        
查询语言KQL、Lucene、Query DSL、ES|QLLogQL，语法接近 PromQL

        
运维复杂度高：分片规划、映射冲突、JVM 调优、集群状态管理较低：可单体起步，规模大后拆成微服务组件

        
多租户借助空间、角色和索引隔离实现原生支持，按租户 ID 隔离

        
生态成熟：SIEM、APM、丰富的 Kibana 可视化与插件与 Grafana、Prometheus、Tempo 深度融合，指标、日志、链路一键跳转

优缺点

  

    

      
ELK

      
优点

      
    
        
  • 任意字段、任意关键词的全文检索都很快，适合不知道要查什么的排障和调查。
    • 
        
  • 聚合与统计分析能力强，可以把日志当数据仓库来做报表。
    • 
        
  • 安全分析（SIEM）、审计、APM 等场景成熟，开箱即用。
    • 
        
  • Kibana 可视化丰富，社区资料和第三方集成多。
    • 
      

      
缺点

      
    
        
  • 存储和内存成本高，日志量到 TB/天级别时费用压力明显。
    • 
        
  • 运维门槛高：分片数、映射爆炸、GC 停顿、集群黄红状态都需要专人照看。
    • 
        
  • 写入链路重，流量突增时通常要加 Kafka 缓冲。
    • 
        
  • Logstash 本身吃资源，复杂的 grok 规则维护成本不低。
    • 
      

    

    

      
Loki

      
优点

      
    
        
  • 成本低：高压缩率加对象存储，长期保留日志也负担得起。
    • 
        
  • 写入轻，水平扩展简单，Ingester 和 Querier 按需加副本即可。
    • 
        
  • 标签体系与 Prometheus 一致，从告警指标到对应日志一键跳转。
    • 
        
  • 原生多租户，部署简单，单个二进制就能跑起来。
    • 
      

      
缺点

      
    
        
  • 没有全文索引，大时间范围的模糊搜索会慢，也更耗查询端资源。
    • 
        
  • 对标签设计要求高：标签太少查得慢，高基数标签又会拖垮集群。
    • 
        
  • 复杂统计分析能力弱，不适合把日志当 BI 数据源。
    • 
        
  • 安全审计、合规类的现成功能和生态较少。
    • 
      

    

  






  
怎么选

  

    
选 ELK，如果
需要对日志做频繁的全文检索和多维分析；有安全审计、SIEM 或业务数据分析需求；日志量可控或预算充足，并且有人维护集群。

    
选 Loki，如果
主要用日志做运维排障，查询习惯是先定位服务和时间再看细节；已经在用 Prometheus 和 Grafana；日志量大且希望长期保留、控制成本。

    
两者混用，如果
规模较大的团队常见做法：全量应用日志进 Loki 保证覆盖和成本，安全审计、交易等需要深度检索分析的少量日志另送一份到 Elasticsearch。

  





说明：ELK 中的 Beats 也可换成 Elastic Agent，Logstash 也可由 Elasticsearch ingest pipeline 替代；Loki 的采集端 Promtail 已停止演进，官方推荐使用 Grafana Alloy。存储比例为量级示意。
