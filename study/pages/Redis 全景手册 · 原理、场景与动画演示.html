    认识 Redis

    Redis（Remote Dictionary Server）是开源的、基于 Key-Value 的 NoSQL 内存数据库，支持网络访问、可持久化，并提供丰富的数据结构。它最常见的定位是客户端与持久化数据库（如 MySQL）之间的缓存层，目的是：减少数据库 IO 压力、提升访问速度（内存比磁盘快 10~100 倍以上）、支撑高并发。

    核心特性

    特性说明软考答题要点
    高性能纯内存操作，单机读写可达 10 万+ QPS适用高并发读，缓解数据库压力
    丰富的数据结构String、Hash、List、Set、ZSet，以及 Geo、HyperLogLog、Bitmap、Stream；Redis 8 起内置 JSON、时序、概率结构、向量集合按业务场景选择合适的结构
    持久化RDB 快照 + AOF 日志，可混合保障数据安全，平衡性能与可靠性
    高可用主从复制、哨兵、Cluster 集群故障转移，避免单点故障
    原子性命令由单线程执行，单条命令天然原子；多条命令用 Lua / 事务保证计数器、分布式锁、扣库存

    缓存三大问题：穿透、击穿、雪崩

    三个问题的共同结局都是“大量请求越过 Redis 直接打到数据库”，区别在于为什么越过。先在模拟器里看看它们的样子，再打开防护对比。

    每个小圆点是一个用户请求，从左往右跑：先到 Redis 查缓存，命中就变绿原路返回，没命中就继续往右去查 MySQL。右边竖条是数据库每秒收到的查询数，超过黄色虚线就扛不住了。带白圈和文字标签的是被跟踪的请求，下方旁白会实时讲它正在经历什么；出现突发情况时，旁白会用黄字提示。建议先看“关闭防护”时的样子，再点“开启防护”对比。

    缓存三兄弟模拟器数据库每秒查询超过 4 次（黄色虚线）即判定过载

    缓存穿透：查一个根本不存在的数据

    定义：请求的 key 在缓存和数据库里都不存在。数据库查不到就不会回写缓存，于是每次请求都直达数据库。多半是恶意攻击（用脚本刷 id=-1、9999999、abc123）。

    例子：商品详情接口被每秒 10 万次刷不存在的商品 ID，MySQL CPU 打满，正常用户也查不了商品。

    方案一：缓存空对象。查不到也缓存 {key:1, value:null}，设置短 TTL。简单，但会占内存，且后来真插入了数据会短暂不一致。

    方案二：布隆过滤器。在 Redis 前加一道拦截：判断为“一定不存在”的直接返回。内存占用小，但实现复杂、存在误判、标准布隆不支持删除（要删用 Cuckoo 过滤器）。实现可用 Redisson 的 RBloomFilter、Guava，或 Redis 8 内置的 BF.ADD / BF.EXISTS。

    布隆过滤器：位数组 + 3 个哈希函数添加会把 3 个位置为 1；查询时 3 位全为 1 才“可能存在”

    已添加：（无）。试试先添加 id1、id2、id3，再查询 id4、hello 等，碰运气撞出一次误判。

    答题要点

    布隆过滤器说“不存在”一定不存在，说“存在”可能误判。误判率与数组长度、哈希函数个数、元素数量有关：数组越大误判越低、内存越多，项目中一般设到 5% 以内（Redisson：tryInit(预期元素数, 0.05)）。缓存预热时同步预热布隆过滤器。

    缓存击穿：一个热点 key 刚好过期

    定义：某个热点 key 过期的瞬间，大量并发请求同时未命中，一起去数据库重建缓存，可能瞬间压垮 DB。

    例子：618 秒杀的 9.9 元耳机缓存恰好在 10:00:00 过期，10 万并发同时查 MySQL，连接被占满。

    方案做法特点
    互斥锁未命中时先 SETNX 抢锁，抢到的线程查库并回写缓存，其他线程休眠后重试读缓存强一致，性能差，有死锁风险（锁要设过期）
    逻辑过期不给 key 设 TTL，而是在 value 里存 expire 字段；读到已逻辑过期时，抢锁开新线程异步重建，当前线程先返回旧数据高可用、性能好，但短时间返回旧数据
    补充热点 key 永不过期（PERSIST）+ 主动更新；活动前预热适合可预知的热点

    缓存雪崩：大量 key 同时失效或 Redis 宕机

    定义：同一时段大量 key 同时过期（设置了相同 TTL），或 Redis 整体宕机，请求洪峰直达数据库。

    例子：生鲜电商把所有商品缓存设为“0 点整过期”，0 点秒杀开始时几千万查询同时打到 MySQL；或机房网络故障导致整个 Redis 集群不可用，打车预估价全部查库。

    方案：TTL 加随机值打散过期时间；Redis 哨兵 / 集群提高可用性；限流降级（Nginx、Spring Cloud Gateway、Sentinel 熔断）；多级缓存（Caffeine / Guava 本地缓存 + Redis）。降级限流可作为三个问题共同的保底策略。

    问题本质产生原因解决方案
    穿透数据根本不存在恶意攻击、误删缓存空值、布隆过滤器、参数校验
    击穿一个热点 key 过期高并发 + 热点过期互斥锁、逻辑过期、预热
    雪崩大量 key 过期 / Redis 挂了相同 TTL、Redis 宕机随机 TTL、集群高可用、限流降级、多级缓存
    口诀

    穿透无中生有 key，布隆过滤 null 隔离；
    击穿过期热点 key，锁与非期解难题；
    雪崩大量过期 key，过期时间要随机；
    面试必考三兄弟，可用限流来保底。

    缓存与数据库一致性（双写一致）

    一份数据同时存在 Redis 和 MySQL，数据变更时两边就可能不一致。回答这类题一定先交代业务背景：是要求强一致，还是允许短暂延迟？方案完全不同。

    几个先要想清楚的选择：

    • 删缓存还是更新缓存？删除。更新缓存在并发写时容易乱序，且很多写入后并不会被读，白白浪费计算。
    • 先删缓存还是先改数据库？两种都有并发问题。“先删缓存再改库”在读写并发时很容易把旧值写回缓存；“先改库再删缓存”出问题需要“读库比写库还慢”，概率低得多，是 Cache-Aside 的标准做法。

    左右两条竖虚线分别是正在改价格的线程 A 和正在查价格的线程 B；中间上方是 Redis 缓存，下方是 MySQL。彩色胶囊是线程发出的命令，从发出方飞向目标，飞到之后目标里的值才会变化并闪烁。红框表示数据错了，绿框表示正确。建议用“下一步”自己点，边看旁白边看图。

    为什么需要“延迟双删”逐步演示读写并发如何把旧值写回缓存
    旁白
    1. 初始：缓存和数据库里都是 10。线程 A 要把价格改为 20，线程 B 同时在读。
    2. A 先删除缓存（第一次删）。
    3. B 读缓存未命中，去查数据库，此时 A 还没改库，B 读到旧值 10。
    4. A 把数据库更新为 20。
    5. B 把刚才读到的旧值 10 写回缓存 —— 缓存与数据库不一致了，而且会一直错到 TTL 过期。
    6. A 休眠一段时间（略大于“读库 + 写缓存”耗时，也要覆盖主从同步延迟）后第二次删除缓存，把脏数据清掉。
    7. 之后的读请求未命中，从数据库读到 20 并回填，最终一致。缺点：延迟多久难以确定，延迟期间仍可能读到脏数据，不是强一致。

    四种同步办法 + 一种强一致办法

    办法真实场景优点缺点 / 适用
    先改库再删缓存电商改价：MySQL 99→89 成功后删缓存，下次读回填简单，九成中小业务够用删缓存失败会短暂不一致；加 TTL 兜底，风险可控
    延迟双删社交 App 改昵称：删缓存→改库→延迟 2 秒再删避免旧数据回写延迟时间难定，仍有极短不一致
    MQ 异步通知外卖改起送价：改库后发 MQ，消费者更新 / 删除缓存，失败自动重试解耦，有重试兜底需要保证 MQ 可靠性，架构复杂，适合中大型系统
    Canal 监听 Binlog直播粉丝数：Canal 伪装成 MySQL 从节点读 binlog，自动更新缓存业务代码零侵入，实时性高要部署运维 Canal
    Redisson 读写锁抢券库存：读加共享锁，写加排他锁强一致性能低，读写方法必须用同一把锁

    Binlog 记录所有 DDL 和 DML 语句，不记录 SELECT、SHOW 等查询语句，Canal 正是基于 MySQL 主从复制协议来拿到这些变更。

    面试 / 软考答法

    ① 文章热点数据：实时性要求不高，允许延迟一致 → 用 Canal 异步同步（不改业务代码）。

    ② 抢券库存：需要实时强一致 → Redisson 读写锁：读读不互斥、读写互斥、写写互斥，写时其他线程读不到脏数据。

    ③ 为什么不用延迟双删：延时多久不好确定，延时期间仍会出现脏数据，不能保证强一致。

    ④ 若业务要求强一致，最稳妥的是不走缓存，直接读数据库；最终一致方案只适合能接受短暂不一致的场景（商品详情、用户信息）。

    四种缓存读写策略

    策略谁负责读写一句话特点
    Cache-Aside（旁路）业务代码读：先缓存后库并回填；写：先改库再删缓存最常用、灵活，本章方案都属此类
    Read-Through缓存组件缓存组件负责从库读并回填业务代码更简洁
    Write-Through缓存组件写缓存时同步写库强同步，写入偏慢
    Write-Behind缓存组件先写缓存，异步批量落库吞吐高，宕机有丢数据风险

    持久化：RDB 与 AOF

    RDB：内存快照

    RDB（Redis Database Backup file）把某一时刻内存中的全部数据写成压缩的二进制文件 dump.rdb，重启时直接加载。

    save       # 主进程执行，阻塞所有命令，几乎不用
bgsave     # fork 子进程执行，主进程继续服务

# redis.conf：满足任一条件自动 bgsave
save 900 1       # 900 秒内至少 1 个 key 被修改
save 300 10
save 60 10000

    左边是 Redis 主进程，右边是 bgsave 时复制出来的子进程。两者各有一张“页表”，可以理解成目录：记录每份数据放在物理内存的哪个位置。连线表示“目录指向这块内存”。重点看第 4 步：主进程要改数据时，它的连线改指向一份新副本，而子进程的连线不动，所以快照不受影响。

    bgsave 如何做到不阻塞：fork + 写时复制页表 = 虚拟地址到物理地址的映射
    旁白
    1. 执行 bgsave 前：主进程通过页表访问物理内存中的数据 A、B。
    2. fork 子进程：只复制页表，不复制数据，父子进程共享同一份物理内存。fork 这一下主进程会短暂阻塞，实例内存越大越久。
    3. 子进程读取共享内存写入新的 RDB 临时文件；主进程照常处理请求，读操作直接访问共享内存。
    4. 主进程收到写命令要改 B：触发写时复制，先拷贝出 B′，主进程页表指向 B′ 再修改。子进程看到的仍是旧 B，快照不受影响。
    5. 子进程写完，用新文件原子替换旧 RDB。快照内容是 fork 那一刻的数据，两次快照之间的写入宕机后会丢。
    写时复制的代价

    写入很频繁时，大量页面被复制，内存可能接近翻倍，所以要给 Redis 预留内存，并关闭 Linux 透明大页（THP），否则一次复制的是 2MB 大页。

    AOF：追加命令日志

    AOF（Append Only File）把每条写命令追加到文件，重启时重放命令恢复数据。默认关闭：

    appendonly yes                   # 开启 AOF，默认 no
appendfilename "appendonly.aof"
appendfsync everysec             # always / everysec（默认）/ no
auto-aof-rewrite-percentage 100  # 比上次重写后增长 100% 触发重写
auto-aof-rewrite-min-size 64mb   # 至少 64MB 才触发
    appendfsync刷盘时机优点缺点
    always每条写命令同步刷盘几乎不丢数据性能影响大
    everysec先写缓冲区，每秒刷一次性能适中最多丢 1 秒数据
    no操作系统决定何时刷性能最好可能丢大量数据
    AOF 重写（BGREWRITEAOF）点几条写命令，再点“重写”，看文件如何被压缩成最少的命令
    
  
    同一个 key 被写多次，只有最后一次有意义。重写由子进程根据内存现状生成新文件，期间新命令写入重写缓冲区，完成后追加并替换。
    

    

    RDB 与 AOF 对比
    

    

    RDBAOF
    

    持久化方式定时对整个内存做快照记录每一条写命令
    

    数据完整性不完整，两次快照之间会丢相对完整，取决于刷盘策略
    

    文件大小压缩二进制，小文本命令，大（可重写）
    

    恢复速度快慢（要逐条重放）
    

    恢复优先级低高：两者都开时，重启优先用 AOF
    

    资源占用fork 时 CPU、内存消耗大平时主要是磁盘 IO；重写时也要 fork
    

    适用容灾备份、能容忍分钟级丢失数据安全要求高，更常见
    

    

    

    业务场景选型理由
    

    纯缓存、可接受少量丢失仅 RDB（甚至都不开）对性能影响小，恢复快
    

    计数、订单等要安全AOF everysec最多丢 1 秒
    

    生产最优解RDB + AOF 混合持久化RDB 快速全量恢复，AOF 补增量
    

    

    混合持久化（4.0+，aof-use-rdb-preamble yes，5.0 起默认开启）：AOF 重写时先把内存写成 RDB 格式作为文件前半部分，之后的增量命令以 AOF 格式追加。兼得 RDB 的恢复速度与 AOF 的低丢失率。Redis 7.0 起 AOF 拆为多文件（Multi Part AOF：base + incr + manifest），重写不再需要重写缓冲区。
    

    软考问答：数据不能丢、又要快速恢复，怎么配？

    ① appendonly yes + appendfsync everysec，兼顾性能与安全，最多丢 1 秒；② 同时开启 RDB（save 900 1 等）用于快速全量恢复；③ 开启混合持久化，定期 BGREWRITEAOF 防止文件过大；④ 重要业务配主从，从节点开 AOF，主节点用 RDB 降低开销。

    过期删除与内存淘汰
    

    key 过期后不会立刻从内存消失。“过期策略”管的是过期的 key 什么时候删，“淘汰策略”管的是内存满了删谁，两者是不同的问题。
    

    三种过期删除策略
    

    

    策略做法优点缺点
    

    定时删除每个 key 一个定时器，到点立刻删内存最友好极耗 CPU，Redis 不采用
    

    惰性删除访问 key 时才检查，过期就删对 CPU 友好没人访问的过期 key 一直占内存
    

    定期删除每隔一段时间随机抽一批带 TTL 的 key 检查删除平衡 CPU 和内存可能漏删，执行时长和频率难定
    

    

    

    定期删除有两种模式：
    

      

    • SLOW 模式：定时任务，频率由 hz 决定（默认 10，即每秒 10 次），每次不超过 25ms。
      • 

    • FAST 模式：每次事件循环前尝试执行，两次间隔不低于 2ms，每次不超过 1ms。
      • 

    

    Redis 的实际做法是“惰性删除 + 定期删除”配合：定期删除批量清理，惰性删除兜底；两者都漏掉的，内存满了由淘汰策略最后处理。
    

    

    八种（8.6 起十种）淘汰策略
    

    

    策略范围规则
    

    noeviction—默认。不淘汰，内存满时写命令报 OOM 错误，读不受影响
    

    volatile-ttl设了 TTL 的 key剩余 TTL 越小越先淘汰
    

    allkeys-random / volatile-random全部 / 有 TTL随机淘汰
    

    allkeys-lru / volatile-lru全部 / 有 TTLLRU：最近最少使用，最久没访问的先走
    

    allkeys-lfu / volatile-lfu全部 / 有 TTLLFU：最不经常使用，访问频率最低的先走（4.0+）
    

    allkeys-lrm / volatile-lrm全部 / 有 TTLRedis 8.6 新增：按“最近最少被修改”淘汰
    

    

    
  
    LRU vs LFU：同样的访问序列，淘汰谁？缓存容量 4，点按钮访问 key，满了再访问新 key 会触发淘汰
    
  
    
    
    
  
    
  
    
    
    LRU · 按最后访问时间（左边最新）
    
    
    LFU · 按访问次数（左边最多）
    
  
    
  
    旁白
    点上面的字母访问对应的 key，或者直接点“演示序列”。
    
  
    例：key1 3 秒前访问、key2 9 秒前访问 → LRU 删 key2；key1 最近访问 4 次、key2 访问 9 次 → LFU 删 key1。
    

    

    

    实现细节：Redis 的 LRU 是近似 LRU，每次随机采样 maxmemory-samples（默认 5）个 key，淘汰其中最久未访问的；LFU 用 8 位对数计数器记录频率，并随时间衰减，避免“曾经很热”的 key 永远不被淘汰。
    

    使用建议
    

      

    1. 有明显冷热区分的纯缓存：优先 allkeys-lru，把最近常用的数据留下。
      2. 

    2. 访问频率差不多、没有明显冷热：allkeys-random。
      3. 

    3. 有置顶 / 必须常驻的数据：volatile-lru，常驻数据不设过期时间就不会被淘汰。
      4. 

    4. 短时间高频访问的数据：allkeys-lfu 或 volatile-lfu。
      5. 

    5. 金融支付等绝不能丢的：noeviction，宁可写失败。
      6. 

    

    

    高频面试题

    数据库有 1000 万数据，Redis 只能存 20 万，如何保证都是热点？ 用 allkeys-lru，留下来的就是最近常访问的热点数据。
    

    Redis 内存用完了会怎样？ 看淘汰策略。默认 noeviction 会直接对写命令报错。注意 64 位系统默认 maxmemory 0 表示不限制，会一直用到系统内存甚至 swap，生产必须显式配置。

    Redisson：生产级实现
    

    Redisson 底层是 SETNX 思路 + Lua 脚本（保证原子性），加锁、设置过期时间、续期都在 Lua 里完成。它解决了三个问题：
    

      

    • 锁的有效期怎么定？业务时长难预估 → 看门狗（WatchDog）自动续期。
      • 

    • 同一线程能否重入？用 Hash 结构存锁：大 key 是锁名，field 是线程标识，value 是重入次数，加锁 +1、释放 -1，归零才删除，避免自己把自己锁死。
      • 

    • 拿不到锁怎么办？tryLock(waitTime, leaseTime, unit) 在等待时间内循环重试，比直接失败性能更好。
      • 

    

    黄色进度条是锁还剩多久自动过期（满格 = 30 秒）。下方左边是 Redisson 在后台运行的“看门狗”定时任务，右边是持有锁、正在执行业务的线程。注意进度条什么时候被重新充满，又在什么情况下不再被充满。

    主从切换会丢锁吗？
    

    

    会。线程 1 在 master 上加锁成功，主从复制是异步的，锁还没同步到 slave，master 就宕机了；slave 被提升为新 master，线程 2 又加锁成功 —— 两个线程同时持有同一把锁。
    

    RedLock（红锁）：在 N 个独立的 Redis 实例上依次加锁，至少 N/2+1 个成功才算加锁成功。缺点是实现复杂、性能差、运维繁琐，并且仍有争议（依赖时钟）。如果业务必须强一致，建议用 ZooKeeper / etcd 实现的分布式锁（CP），而 Redis 属于 AP 思路。
    

    

    Redisson 分布式锁一句话总结
    SETNX + Lua 保原子；Hash 记录线程与重入次数；WatchDog 自动续期；可控制重试等待；RedLock 解决主从丢锁但性能差；要强一致就用 ZooKeeper。
    


    Redis 事务：MULTI / EXEC / DISCARD / WATCH
    

    

    命令作用答题要点
    

    MULTI开启事务，后续命令进入队列事务开始标记
    

    EXEC按顺序执行队列中的全部命令执行期间不会被其他客户端插队，但不保证经典 ACID
    

    DISCARD放弃事务，清空队列—
    

    WATCH监视 key，EXEC 前被改动则事务失败返回 nil乐观锁实现
    

    

    命令入队时有语法错误，整个事务都不执行；EXEC 时某条命令运行出错（例如对字符串执行 INCR），只有这条失败，其余照常执行，不会回滚。所以 Redis 事务的核心价值是“打包顺序执行 + WATCH 乐观并发控制”，复杂逻辑更推荐 Lua 脚本或 7.0 的 Functions。
    

    两个客户端同时想买最后一件商品。下方的“队列”表示：MULTI 之后发出的命令只是排队，还没执行；直到 EXEC 才真正执行，或者整体被放弃。

      3.

      4.

      5. 
    
    5. 客户端 2 EXEC：发现 stock 在 WATCH 之后被改过 → 返回 nil，队列里的命令全部不执行。
      6. 
    
    6. 客户端 2 重试：重新 WATCH 读到 0，判定已抢完。Redis 8.4 起单 key 场景还可以直接用 SET key new IFEQ old 做比较并设置（CAS）。

    悲观锁 vs 乐观锁
    

    

    维度悲观锁乐观锁
    

    思想认为冲突大概率发生，先加锁再操作认为冲突小概率发生，提交时校验
    

    加锁时机操作前加锁（阻塞）不加锁（非阻塞）
    

    适用场景写多、强一致（秒杀扣减）读多写少的读-改-写（点赞、计数）
    

    Redis 实现SET NX EX / Redisson 排他锁WATCH + MULTI/EXEC；8.4+ SET IFEQ
    

    数据库实现SELECT … FOR UPDATEversion 字段：update … set version=version+1 where version=?，影响行数 0 即冲突重试
    

    优缺点安全但性能低，可能死锁性能好，冲突多时重试多
    

    

    记忆锚点
    悲观锁 = 先锁后干、动辄阻塞（setnx）；乐观锁 = 放手去干、提交把关（WATCH + MULTI）。
    项目答法：抢券库存强一致、高冲突 → Redisson 排他锁；文章点赞读多写少、冲突低 → WATCH 乐观锁。
    

    Redis 的线程安全问题
    

    服务端：命令由主线程串行执行，单条命令天然原子，不存在线程安全问题（6.0 的多线程只处理网络 IO）。客户端：多个客户端“先 GET 再 SET”这种读-改-写组合不是原子的，会有竞态。解决：尽量用原子命令（INCR、DECR、SETNX、HINCRBY），或用 Lua 脚本把多条命令打包成原子操作。

    部署模式架构优点缺点适用
    

    单机单实例简单单点故障、容量受限开发测试

    主从复制：全量同步与增量同步
    

    单节点并发能力有上限，主从集群实现读写分离：主写从读。同步靠两个标识：
    

    • Replication Id（replid）：数据集标记，id 一致说明是同一数据集。每个 master 有唯一 replid，slave 会继承 master 的 replid。
      • 

    • offset：偏移量，随写入 repl_backlog 的数据增多而增大。slave 的 offset 小于 master 的，说明落后了。
    

    左边竖线代表 master（主节点），右边代表 slave（从节点），胶囊是两者之间传递的消息。记住两个“身份证”：replid 是数据集编号，相同说明从节点“认识”这个主节点；offset 是已经同步到第几条。底部左边是主节点的复制缓冲区，右边是从节点本地数据的状态。
    

    
  
    主从同步全过程前 6 步是全量同步，后 2 步是增量同步
    
  
    
  
    旁白
      
    
    1. slave 执行 replicaof <masterip> <port>，与 master 建立连接。
      2. 
    
    2. slave 请求同步，带上自己的 replid 和 offset（第一次是 PSYNC ? -1）。
      3. 
    
    3. master 判断 replid 不一致 → 是第一次同步，回复 FULLRESYNC，把自己的 replid 和 offset 发给 slave 保存。
      4. 
    
    4. master 执行 bgsave 生成 RDB；生成期间收到的写命令记录到 repl_backlog。
      5. 
    
    5. master 发送 RDB，slave 清空本地数据，加载 RDB。
      6. 
    
    6. master 把 backlog 中 RDB 生成期间的命令发给 slave 执行，全量同步完成。之后 master 持续把写命令传播给 slave。
      7. 
    
    7. slave 重启或断线重连：PSYNC 带上已有的 replid 和 offset=1003。
      8. 
    
    8. replid 一致 → 不是第一次，回复 CONTINUE，从 backlog 中取 offset 之后的命令补发：增量同步。若断开太久，offset 对应的数据已被环形缓冲区覆盖，只能退回全量同步。
      9. 
  
    
  
    

    

    软考答题要点
    主从复制实现读写分离（主写从读）与数据冗余，但主节点存在单点故障风险，需要人工介入或配合哨兵自动故障转移。优化：适当调大 repl-backlog-size 减少全量同步；无磁盘复制 repl-diskless-sync；控制单节点内存，减少 RDB 体积。
    


    哨兵（Sentinel）
    

      

    • 监控：每秒向每个实例发 PING，检查是否按预期工作。
      • 

    • 自动故障恢复：master 故障时把一个 slave 提升为 master；故障实例恢复后以新 master 为主。
      • 

    • 通知 / 配置中心：充当客户端的服务发现来源，故障转移后把新地址推送给客户端。
      • 

    

    主观下线：某个哨兵发现实例在规定时间内未响应。客观下线：超过 quorum 个哨兵都认为它主观下线，quorum 最好超过哨兵数量的一半。

    分片集群（Redis Cluster）
    

    主从和哨兵解决了高可用和高并发读，但解决不了海量数据存储和高并发写。分片集群的特征：
    

      

    • 多个 master，每个保存不同数据；每个 master 可以有多个 slave。
      • 

    • master 之间通过 PING（Gossip 协议）检测彼此健康，故障时 slave 自动晋升，不需要哨兵。
      • 

    • 客户端访问任意节点，最终都会被转发到正确节点（MOVED / ASK 重定向，智能客户端会缓存槽位表）。
      • 

    • 16384 个哈希槽：CRC16(key) % 16384 决定槽位，每个 master 负责一段。如果 key 含 {}，只用大括号里的部分计算（Hash Tag），可让相关 key 落在同一槽。
      •

    master B · 5461–10922
    master C · 10923–16383
    
  
    

    

    

    为什么是 16384 个槽？节点间心跳要携带自己负责的槽位图，16384 位 = 2KB，在带宽与粒度之间取得平衡；官方建议集群不超过约 1000 个 master。
    

    限制：多 key 命令（MGET、事务、Lua）要求所有 key 在同一槽，用 Hash Tag 解决；只能用 0 号库。Redis 8.4 新增原子槽迁移（CLUSTER MIGRATION）：先把整个槽的数据和增量复制到目标节点，再一次性切换归属，迁移中客户端不再频繁遇到重定向。
    

    


    一致性哈希（对比哈希槽）
    

    普通取模 hash(key) % N 在节点数变化时几乎所有 key 都要搬家。一致性哈希把节点和数据都映射到一个环上，数据顺时针找最近的节点，增删节点只影响相邻一段。节点少时容易数据倾斜，用虚拟节点打散。
    

    
  
    一致性哈希环点“添加节点 D”，被迁移的 key 会加上白圈
    
  
    
  
    
  
    

    

    

    维度哈希槽（Redis Cluster）一致性哈希
    

    寻址CRC16(key) % 16384 → 槽 → 节点哈希环上顺时针找节点
    

    节点变化按槽重新分配，可精确控制迁移哪些槽只迁移相邻一段数据
    

    均衡槽可手动均分需要虚拟节点辅助
    

    代表Redis ClusterMemcached 客户端分片、Codis 之前的方案、多数分布式缓存

    用户空间、内核空间与三种 IO 模型
    

    

    Linux 进程内存分为用户空间（Ring3，只能执行受限命令，访问资源要通过内核接口）和内核空间（Ring0，可调用一切系统资源）。读数据分两步：① 等待数据到达内核缓冲区；② 从内核缓冲区拷贝到用户缓冲区。

    IO 多路复用一个线程同时监听多个 Socket，就绪才通知阻塞—，充分利用 CPU

    Redis 做消息队列
    

    Redis 有四种方式实现消息传递，可靠性依次增强。选哪个，取决于“消息丢了能不能接受”。
    

    

    方式核心命令持久化ACK / 重试多消费者适用
    

    ListLPUSH + BRPOP；可靠版 BLMOVE 到“处理中”列表随 RDB/AOF无原生 ACK竞争消费，一条只给一人简单异步任务
    

    Pub/SubPUBLISH / SUBSCRIBE / PSUBSCRIBE；7.0 起 SPUBLISH 分片不存储，发完即丢无广播，所有订阅者都收到实时通知、配置刷新、聊天室
    

    ZSet 延时队列ZADD score=执行时间戳；ZRANGEBYSCORE 取到期的，Lua 中 ZREM 抢占随 RDB/AOF需自行实现竞争订单超时取消、延迟重试
    

    Stream（5.0+）XADD、XREADGROUP、XACK、XPENDING、XAUTOCLAIM持久化消息日志有 ACK + PEL消费组：组内竞争，组间广播轻量可靠消息队列
    

    

    顶部一排是 Stream 中的消息（编号 1-0、2-0、3-0）。中间左边是消费组的进度，右边的 PEL 是“已经发出去、但消费者还没回复处理完”的消息清单。底部是两个消费者。消息框的颜色表示它分给了谁，变绿表示已确认处理完毕。

    热点 Key 与大 Key
    

    

    热点 Key
    问题：某个 key（秒杀商品）被超高并发访问，集群中单个节点被打满。
    发现：redis-cli --hotkeys（需 LFU 策略）、客户端埋点、Redis 8.6 新增的 HOTKEYS 命令。
    处理：本地缓存（Caffeine）承接、key 加后缀拆成多份分散到不同节点、读写分离、热点预热。
    

    大 Key（bigkey）
    问题：value 太大（如几 MB 的 String、几十万元素的 Hash），读写和删除阻塞主线程、网络拥塞、集群内存不均、迁移慢。
    发现：redis-cli --bigkeys / --memkeys、MEMORY USAGE key、离线分析 RDB。
    处理：拆分成多个小 key、压缩序列化、用 UNLINK 异步删除、慎用 HGETALL / SMEMBERS，改用 HSCAN / SSCAN。
    

    

    多级缓存架构
    

    请求依次经过：
    

    1. CDN：静态资源。
    2. Nginx：页面级缓存 / OpenResty 本地缓存。
    3. 进程内本地缓存（Caffeine / Guava）：单机最快，承接热点。
    4. Redis：分布式共享缓存。
    5. 数据库：最终数据源。
    

    一级失效逐级降级，这正是“缓存雪崩用多级缓存兜底”的架构级落法。多级缓存的难点是各级之间的一致性：本地缓存通常设较短 TTL，或通过 MQ / Redis Pub/Sub 广播失效通知。
    


    Redis 变慢了怎么排查
    

    正常响应应在毫秒级（<10ms）。超过 100ms 甚至秒级，按以下顺序排查：
    

      

    1. 测基线：redis-cli --intrinsic-latency 60 测服务器本身在无压力时的延迟，判断是不是机器太差。
      2. 

    2. 确认真的是 Redis 慢：PING、INFO stats、--latency，排除网络（跨机房、带宽）和客户端连接数过多。
      3. 

    3. 慢查询：SLOWLOG GET 查复杂度高的命令（KEYS、HGETALL、大范围 ZRANGE、SORT），优化命令、拆分大 key。
      4. 

    4. 集中过期：同一时刻大量 key 过期会让主线程长时间删除 → TTL 加随机数。
      5. 

    5. 大 key：--bigkeys 扫描，避免写入大 key，删除用 UNLINK。
      6. 

    6. 持久化与 fork：INFO 里的 latest_fork_usec；AOF 刷盘与重写竞争磁盘 IO 时，可设 no-appendfsync-on-rewrite yes（重写期间暂停 fsync，有丢数据风险），AOF 放 SSD。
      7. 

    7. 系统层面：CPU 绑核、是否使用了 swap（禁用）、关闭透明大页、磁盘 IO。
      8. 

    8. 仍不行：升级版本或拆分集群。
      9. 

    


    秒杀 / 高并发系统串讲（论文素材）
    

    把全部考点串成一条链路：
    

      

    1. 用户请求先经 Nginx + Redis 令牌桶限流，挡掉超额流量和刷子。
      2. 

    2. 活动前预热：热点商品、库存、布隆过滤器提前加载进缓存，热点 key 永不过期，防击穿和穿透。
      3. 

    3. 扣库存用 Lua 原子扣减或 Redis 分布式锁精准放行，防超卖。
      4. 

    4. 下单请求进入 MQ 削峰，异步落库。
      5. 

    5. 数据库变更通过 Canal / MQ 异步同步缓存，保证最终一致。
      6. 

    6. 底层 Redis 采用哨兵或 Cluster 保证高可用，RDB + AOF 混合持久化，多级缓存兜底雪崩。

    向量检索：Redis 进入 AI 场景
    

    

    大模型把文字、图片等转换成一串数字，叫向量（Embedding），意思相近的内容向量也相近。“找最相似的 K 个”就是向量检索，常用于语义搜索、RAG 召回、推荐、语义缓存（问法不同但意思相同的问题直接复用 LLM 的回答，省钱又快）。
    

    Redis 提供两套方案：
    

      

    • Vector Set（8.0 新类型）：像 ZSet 一样简单，元素关联一个向量而不是 score。由 Redis 作者 antirez 设计，基于 HNSW 算法，支持量化（默认 int8，也可 BIN 二值化或不量化）和按属性过滤。
      • 

    • Redis 查询引擎（原 RediSearch）：在 Hash / JSON 上建向量索引，支持 FLAT（精确）/ HNSW / SVS-VAMANA，能与全文、数值、地理条件组合；8.4 的 FT.HYBRID 用 RRF 等方法融合关键词与语义排名。
      •

    四类 NoSQL

    软考选型答题范式
    先判断属于哪一类 NoSQL，再从读写特性、数据模型、一致性需求、扩展性、运维成本五个维度对比。补充：向量数据库（Milvus、Redis 向量检索）已成为第五类常见选型。
    

    CAP 定理
    

    分布式系统中一致性（C）、可用性（A）、分区容错性（P）不可兼得。网络分区不可避免，所以实际是 CP 或 AP 二选一：
    

    • CP：放弃可用性保一致 —— ZooKeeper、etcd、HBase，银行转账。
      • 

    • AP：放弃强一致保可用 —— 大部分缓存场景、Redis、购物车、非核心展示数据。
    

    Redis 默认主从异步复制，通常归为 AP（可用性优先、最终一致）。可以用 WAIT 命令等待指定数量的从节点确认，提高一致性，但仍不能保证强一致。
    

    BASE 理论
    

    Basically Available（基本可用）+ Soft state（软状态）+ Eventually consistent（最终一致）。BASE 是 AP 的延伸，也是“缓存允许短暂不一致”的理论依据，与第 4 章的双写一致性方案呼应。
    

    一致性强度从强到弱：强一致 → 顺序一致 → 因果一致 → 最终一致 → 弱一致。讲清“Redis 默认提供最终一致”即可命中考点。
    

    分布式事务方案
    

    

    方案一致性原理适用
    

    2PC强一致准备 + 提交 / 回滚，协调者统一决策参与者少、要求强一致；有同步阻塞、协调者单点问题
    

    3PC较 2PC 改进增加“预提交”阶段和超时机制，减少阻塞改进单点 / 阻塞，但仍可能不一致
    

    TCC最终一致Try 预留资源 → Confirm 确认 / Cancel 补偿可逆的分布式业务，代码侵入大
    

    可靠消息（MQ）最终一致本地事务 + 发消息 + 消费重试与缓存双写的 MQ / Canal 方案同源
    

    Saga最终一致长事务拆成多个本地事务，失败时逆序补偿长流程业务

    勘误与考前速记
    

    原资料中需要澄清的地方
    

    整理时发现的问题

    ① Memcached 是多线程的，原表格写“单线程”不准确；“Redis 比 Memcached 快 10 倍”缺乏依据，两者简单 KV 性能接近。
    

    ② 两份资料的淘汰建议冲突（“90% 场景选 volatile-lru”与“优先 allkeys-lru”）：纯缓存优先 allkeys-lru；缓存和必须常驻的数据混在一起时用 volatile-lru。
    

    ③ Cluster 并非完全不支持事务、Lua、MGET：只要所有 key 在同一个槽（用 Hash Tag）就可以使用。
    

    ④ 定期删除“每天抽 10 分钟”是比喻，实际是 hz=10（每秒 10 次）、每次不超过 25ms。
    

    ⑤ 主从同步里“缓冲区是一个日志文件”不准确：repl_backlog 是主节点内存中的环形缓冲区。
    

    ⑥ Redisson 的锁底层是 Lua + Hash（HINCRBY 记录重入次数），语义上等同 SET NX，而不是直接调用 SETNX 命令。
    

    ⑦ LRU 通译为“最近最少使用”（按最后访问时间），LFU 为“最不经常使用”（按访问频率）。
    

    ⑧ 排查 AOF 导致的变慢时，把 appendfsync 改为 no 会大幅增加丢数据风险，应先评估业务能否接受。
    

    

    速记卡
    

    

    为什么快
    内存 + 单线程无锁 + IO 多路复用（epoll）。
    

    缓存三兄弟
    穿透：布隆 / 空值；击穿：互斥锁 / 逻辑过期；雪崩：随机 TTL / 集群 / 降级 / 多级缓存。
    

    双写一致
    允许延迟：先改库再删缓存 + MQ / Canal；强一致：Redisson 读写锁。
    

    持久化
    RDB 快照恢复快会丢；AOF everysec 最多丢 1 秒；生产用混合持久化。
    

    过期与淘汰
    惰性 + 定期删除；默认 noeviction；纯缓存 allkeys-lru。
    

    分布式锁
    SET NX EX + Lua 释放；Redisson 看门狗 30s / 10s 续期、Hash 可重入；红锁 N/2+1；强一致选 ZooKeeper。
    

    事务
    MULTI 排队、EXEC 执行、不回滚；WATCH = 乐观锁。
    

    高可用
    主从：replid + offset，全量 / 增量；哨兵：SDOWN → ODOWN → 选领头 → 选新主；脑裂：min-replicas。
    

    Cluster
    16384 槽，CRC16(key) % 16384，Hash Tag 让 key 同槽，MOVED / ASK 重定向。
    

    消息队列
    List 简单无 ACK；Pub/Sub 不持久；Stream 消费组 + ACK + PEL。
    

    CAP
    Redis 是 AP + 最终一致（BASE）；ZooKeeper 是 CP。
    

    Redis 8
    开源回归 AGPL；内置 JSON / 时序 / 布隆 / 向量集合；8.4 混合检索与原子 CAS。
